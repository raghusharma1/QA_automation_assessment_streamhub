# AI pair-programming log

A running record of how Claude Code was used on this project: where it helped, where it was wrong,
and how each error was caught. The README's "Claude Code reflection" section is a summary of this log.

Entry types: ✅ helped · ❌ AI was wrong (and how it was caught) · 🔍 found by review

## Milestone 0: research and recon

| Type | What happened                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ✅   | Parallel research agents compared playwright-bdd and @cucumber/cucumber, checked current package versions on npm, ran the SQL queries on PostgreSQL (PGlite) and SQLite, and sent real POSTs to JSONPlaceholder (it returns 201 for anything, and 500 for malformed JSON).                                                                                                                                                                                                                                                                                                                                                                                   |
| ❌   | **Conflicting TypeScript advice.** One agent said to pin TS 6.0.3, another said 5.9 because "latest is 7.0.2". Checked against the registry: `typescript-eslint@8.71.0` declares `typescript >=4.8.4 <6.1.0`. So 6.0.3 is right, and 7.x would break linting.                                                                                                                                                                                                                                                                                                                                                                                                |
| ❌   | **Hallucinated import.** The `eslint-plugin-playwright` README imports `defineConfig` from `@eslint/config`, a package that doesn't exist on npm (the research agent got a 404). The correct import is `eslint/config`.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ❌   | **Locator that looked right but wasn't.** `getByRole('link', { name: 'Personal Loan' })` looks like the obvious locator, but live recon showed it matches 2 elements (accessible names match on substrings) and fails strict mode. Fixed with `{ exact: true }`. `playwright-cli generate-locator` fell back to `#personal-loan a` for the same reason. **Correction (M6):** this did not reproduce later. The same locator resolves to one element in every Playwright run, with or without ad blocking. The 2-element result came from one playwright-cli session, most likely a transient third-party element. `exact: true` stays as a defensive choice. |
| ✅   | **Race condition found in recon.** Reading the EMI text immediately after `fill` + Tab returned a stale value (`24,126`, which is the 20-year EMI) before the site recalculated. That is why every result check uses a web-first `expect(...).toHaveText()`, which retries until it matches.                                                                                                                                                                                                                                                                                                                                                                 |
| ✅   | The static source analysis said "5 bars if the schedule starts in January, otherwise 6". Live recon confirmed 5 year-categories (10 stacked segments) for a Jan 2027 start.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ❌   | **Destructive command by a sub-agent.** A research agent stopped its prototype server with `taskkill /F /IM node.exe`, which killed every Node process on the machine. The rule since then: never kill processes by image name.                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Milestone 2: TC1 (home loan pie chart)

| Type | What happened                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅   | The EMI oracle was written test-first: 11 unit tests pin the formula and the site's rounding convention (totals come from the unrounded EMI; `round(emi) * n` would be off by ₹27 for the personal loan).                                                                                                                                                                                                                                                                   |
| ✅   | **Mutation check.** The oracle was broken on purpose (rate × 1.01). Both TC1 scenarios failed precisely (`expected ₹33,176, received ₹33,038`), which shows the UI is checked against an independent value and not compared with itself. The change was reverted.                                                                                                                                                                                                           |
| ✅   | The pie chart DOM only shows rounded percentages, so the tests read both the visible labels and the Highcharts model and cross-check them against the oracle (principal exact; interest to the rupee; labels to 1 dp).                                                                                                                                                                                                                                                      |
| ❌   | My first draft imported a helper (`requireLoan`) from one steps file into another. Step files should only register steps, so the helper was moved to the fixtures module.                                                                                                                                                                                                                                                                                                   |
| 🔍   | **Stale-chart race that I missed.** The evaluator found that the "> 0" pie step read values and took its screenshot _before_ the step that waited for the redraw. With a slower redraw it could have checked the page's default chart (also > 0) and passed for the wrong reason. My mutation check proved the tests catch a wrong oracle, but not a stale chart. Fixed with a reusable `waitForChartData()`: every chart read now waits until the model equals the oracle. |
| 🔍   | The "navigate to Home Loan" post-condition proved nothing, because Home Loan is preselected and its label is visible on load. Live recon showed the site marks the selected tab only with `li.active` (no `aria-selected`), so that state is now asserted.                                                                                                                                                                                                                  |
| ❌   | **Control characters injected by my own tooling.** I wrote `/\bactive\b/` through a Python heredoc, and the shell/Python escaping turned `\b` into literal backspace bytes, so the regex could never match. Caught by checking the bytes with `cat -A` before running. Rule since then: edit code containing regex escapes with the exact-replace tool, not shell string escaping.                                                                                          |
| ✅   | A plain Scenario Outline title made the report rows show "Example #1/#2". Instead of guessing, I checked the installed playwright-bdd source and used its `# title-format:` comment, so rows now read "Scenario A - 25L at 10% for 10 years".                                                                                                                                                                                                                               |

| ✅   | The start month is computed relative to today ("January of next year"), and the expected bar count comes from the oracle, so the test works on any run date and never expires. Two Examples show the count changing with the start month (January → 5 bars, June → 6).                                                                                                                                                                                                       |
| ❌   | **Flaky hover found by a repeat run.** Hovering by `mouse.move()` to coordinates from `getBoundingClientRect()` failed once: the tooltip never appeared, because the previous screenshot had scrolled the page and the coordinates went stale. Fixed by turning the data-located SVG element into a normal Playwright locator (keeping actionability checks) and retrying hover + tooltip check with `expect().toPass()`. Then 25/25 passed (5× each, 4 workers, live site). |
| ✅   | **Mutation check.** Shifting the oracle's schedule by one month made both TC2 scenarios fail on the "chart redrawn" wait, so the bar checks really depend on the independent schedule. Reverted.                                                                                                                                                                                                                                                                             |
| ❌   | **Measurement mistake.** Running with `--reporter=line` on the CLI _replaces_ the configured reporters, so no JSON/HTML report was written and my evidence script read an old file. The final evidence run must use the configured reporters.                                                                                                                                                                                                                                |
| 🔍   | **Misleading failure location.** The evaluator found that an oracle/app value mismatch was reported as a failure of the "bar chart is visible" step. Split into a structural "settled" wait (year categories) and a separate values step. A re-run of a mutation (interest +0.1%) now fails exactly in "the yearly interest and principal in the bar chart match my amortization schedule".                                                                                  |
| 🔍   | The hover retry resolved the bar once, outside `toPass()`, so a redraw between attempts couldn't be recovered. The bar is now re-resolved on every attempt, and retries are recorded as a `hover-retry` annotation (0 in a 10-run stability check, which shows the actionability-based hover fixed the root cause). The tooltip is now asserted with a retrying `toHaveText` built from the oracle.                                                                          |

## Milestone 4: B1 API and B2 API tests

| Type | What happened                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅   | The API was designed matrix-first (`api/README.md`: endpoint × parameter × expected status), and the feature files were written from that matrix. `season` on `/api/matches` is **required**, so "missing required parameter" is genuinely tested.                                                                                                                                                                                           |
| ✅   | **Contract independence is enforced, not just intended.** The test-side zod contracts are hand-written from the README, and an ESLint `no-restricted-imports` rule blocks tests from importing `api/src`. It was checked with a probe file, which failed lint.                                                                                                                                                                               |
| ❌   | **Two wrong hand-counted expectations.** I wrote `maxRuns=100 → 6 players` (correct: 5) and the wrong ids for page 2 of `sort=-runs`. Both were caught _before_ running, by counting from the raw JSON with a separate script (not through the API), and fixed in the feature file.                                                                                                                                                          |
| ✅🐛 | **The tests found a real bug in my API.** The property check "items are ordered by name ascending" failed: the API sorted with `<`, which compares UTF-16 code units, so "MS Dhoni" came before "Mohammed Siraj" (capital `S` < lowercase `o`). Fixed with `Intl.Collator('en', { sensitivity: 'base' })`, and the sort rule is now documented.                                                                                              |
| ✅   | **Mutation checks on the API.** Ignoring the team filter → 2 failures. An extra field in the player payload → strict contract failure. Removing the players query validator → 23 failures.                                                                                                                                                                                                                                                   |
| ❌   | **An ineffective mutant.** My first "bypass validation" mutant still ran behind the validator middleware, so all tests passed. I investigated instead of concluding the tests were weak: it was an equivalent mutant. The real bypass (removing the validator) is the one recorded above.                                                                                                                                                    |
| ✅   | The API is decoupled from the test framework (its own port config). The lint rule also forbids `api/` from importing `src/`.                                                                                                                                                                                                                                                                                                                 |
| 🔍   | **My README claimed coverage that didn't exist.** The evaluator found the matrix listed teams `sort=name` (and other happy-path parameters) as tested when no scenario sent them. Fixed by adding the missing scenarios: every sort field in both directions, a multi-key tie-break on a real 435-run tie, matches paging and `sort=-id`. The matrix now has a "Covered by" column naming the scenario for every row. 65 → 78 API scenarios. |
| 🔍   | **An inconsistency in my own API rule.** "Unknown parameters are rejected" was not true on `/health` and `/api/players/:id` (`?foo=1` returned 200). Both routes now validate an empty strict query. `Allow` is now `GET, HEAD`, because Hono serves HEAD for every GET route.                                                                                                                                                               |

## Milestone 5: B4 SQL

| Type | What happened                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅   | Definitions were written before any SQL (`sql/README.md`): 10% of the _original_ amount, inclusive; inclusive 24h, return strictly after the original; streaks over consecutive _appearances_ (primary) or consecutive _team matches played_ (alternative).                                                                                                                                                          |
| ✅   | **One dataset for API and SQL.** Scenario 2's `seed.sql` is generated from `api/data/*.json` plus hand-curated `innings.json`. A test fails if the committed seed drifts from its sources.                                                                                                                                                                                                                           |
| ✅   | **Expected rows were hand-derived before the queries ran,** and all 6 SQL result sets matched on the first run. Edge cases sit on real fixtures from the shared data, including the 2024 washout (match 19) that forced a precise rule for "a match played".                                                                                                                                                         |
| ✅   | **Mutation checks are automated, not one-off.** 11 tests mutate a query (`<=` → `<`, 10% → 11%, 24h → 25h, `>= 30` → `> 30` / `>= 29`, dropping the season or abandoned filter) and assert the result changes in exactly the expected way. That proves every seeded boundary is load-bearing.                                                                                                                        |
| ❌   | **A design choice I corrected before coding.** I first planned to decide whether a fixture was "played" by checking whether batting rows exist. That makes the answer depend on how complete the seed is, so it became an explicit `abandoned` flag instead.                                                                                                                                                         |
| ✅   | PGlite runs the real PostgreSQL engine in-process (no install). DATE/TIMESTAMP/NUMERIC are read as raw text, so the expected rows compare exactly what psql prints, with no JS Date time-zone shifts and no float conversion of money.                                                                                                                                                                               |
| 🔍   | **Weak mutants.** The evaluator found that most scenario-2 mutants only asserted that something was _absent_, so a mutant that broke the query some other way could pass for the wrong reason. Every mutant now asserts its full result, hand-derived from the seed. Three mutants were added: the return direction (3-party cycle), the LAG/LEAD "previous < 30" guard, and filtering the season _after_ numbering. |
| 🔍   | **The same bug twice.** The API tests had already caught a case-ordering bug (code-unit vs alphabetical). The evaluator found that PGlite uses the `C` collation, so `ORDER BY player_name` would differ on a default `en_US` server. I hadn't carried the lesson from the API over to the SQL. The ordering is now explicit (`COLLATE "C"`) and documented.                                                         |
| 🔍   | `abandoned` was inferred from "no winner", which would misflag a tie or a no-result after play. It is now explicit data (`abandonedMatchIds`). A ping-pong A→B→A→B case was added, and the time-zone semantics are documented.                                                                                                                                                                                       |
| ✅   | **Provenance.** The committed result outputs now have a drift check (the tests fail if `sql/results/*.txt` is stale). Screenshots show the server `version()`, and the schemas are captured as images. A script runs everything with real `psql` on `postgres:18` in a throwaway Docker container. PostgreSQL 18.6 returned exactly the rows expected from PGlite.                                                   |
| ❌   | **My own script bugs, caught on the first run.** `DROP DATABASE` inside a multi-statement `psql -c` failed (it runs as a transaction). My first transcript trick (`\i /dev/stdin` with a fallback) could have hidden errors, so it was replaced with plain `psql -a` echo mode.                                                                                                                                      |
